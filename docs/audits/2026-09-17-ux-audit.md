# Full app design, UI and UX audit — 17 September 2026

## Scope and evidence

Read-only review using `interface-design` and `product-design-and-ux`. Reviewed the App navigation/render inventory, every view's rendered structure, major shared navigation/settings/voice components, and relevant stylesheet rules. No AGENTS.md or `.interface-design/system.md` was found in the workspace inventory. User reports and supplied screenshots provide direct evidence of clipped voice-call content, confusing disabled cloning controls, engine discovery trouble, speech correction friction and image-request failures.

This is a code-grounded heuristic audit, not a claim that every provider operation or screen state was exercised live. No paid generation, real call, billing action, participant study or external account modification was performed by this audit agent. Root is conducting debugging/verification separately. Line references describe the current checkout and can move after other agents' edits.

## Direction

The person is creating a character, talking to them and producing media; they should see the next useful action immediately. Domain: character identity, reference recordings, auditions, scenes, drafts, takes, renders and finished assets. Physical color world: charcoal equipment, warm ivory script paper, brushed gold controls, smoke glass, muted brown leather and amber recording lights. Retain the existing warm charcoal/ivory/gold studio direction. Make the persistent active-persona identity and output tray the signature shared across creation, conversation and editing.

Avoid: a rainbow of provider-colored buttons; identical large promotional cards for each task; and advanced model catalogs leading the experience. Instead use one gold next action, a compact task selector and a recommended engine with optional expert controls.

## Prioritized findings

### P1 — One viewport contract for conversations and live calls

Evidence: `src/App.tsx:1201` owns a scrolling main area; `src/views/AssistantView.tsx:3886` consumes h-full; the active call at `:4508` is a scrolling absolute overlay with header, status, 144px avatar, waveform and transcript; the transcript at `:5090` has its own overflow. `CreatePersonaPage.tsx:1427` uses min-h-screen inside the application shell. Gallery, Settings, Voice and Planner also own nested scrolling wrappers. These combinations create competing scroll surfaces and consume height already occupied by the app top bar and breadcrumbs. The user's screenshots show the exact consequence.

Recommendation: define separate shell modes. Workspace forms have one vertical page scroll. Chat/agent/call use a height-constrained min-h-0 flex or grid workspace with fixed compact header and fixed bottom actions; only transcript/results scroll. In live calls, the conversation should dominate and the avatar/waveform should be a small status element; reduce/remove decorative animation at short viewport heights. Provide an optional expanded avatar view. Keep Mute, End call and text input visible at all times.

Acceptance: at 1280×800 and 1440×900 browser content areas, including 125% zoom, header/status, current message, mute/end and input appear simultaneously with no outer-page scroll. Long history may scroll inside its own transcript; “everything visible” cannot mean displaying unlimited history simultaneously. At 390×844, controls remain reachable above safe-area navigation and virtual keyboard.

### P1 — Explain disabled actions at the action, before the user gets stuck

Evidence: `CreatePersonaPage.tsx:2369` disables Render voice for saving/cloning, unavailable model, missing permission/files/transcript or existing clone result, but none of those reasons appears beside the disabled button. Preview/Save at `:2404–2407` also combine several invisible prerequisites. The user's disabled-render screenshot demonstrates confusion.

Recommendation: show a short readiness checklist directly above the primary action, derived from the same validation result used by the handler: recording added, permission confirmed, required transcript present, provider supported. Show one actionable unmet requirement and link/focus it. Display provider limitations before selection. A completed result should show “Use this voice” and “Create another”, rather than leaving Render silently unavailable. Keep the existing Stop waiting control (`:2370`) but distinguish stop waiting from canceling provider work, including whether a render can still finish.

Acceptance: every disabled paid/primary action has a visible reason and next step; changing a recording/model returns the correct readiness state; ready/failed/verification-required/waiting all have a clear recovery action.

### P1 — Make voice choice consistent and audible everywhere

Evidence: `src/components/AvailableVoices.tsx:4–13` exposes name/provider/gender/accent/tone and selection but has no per-voice playback control. Account voice cards in `CreatePersonaPage.tsx:2220` and `:2345` provide previews; other voice flows have different pickers. `PersonaControls.tsx` exposes engine selection separately from saved voice. The user explicitly asked for a play icon beside each voice.

Recommendation: reuse one voice row/card for Available voices, saved voices, account voices and Agent controls. Separate Select from Listen; show provider, compatible engines, natural language/accent and whether audio is a prerecorded sample or a new generated audition. Only one sample plays at a time. Show sample unavailable/loading/error states and an explicit retry. Deduplicate provider+voice IDs before rendering (`AvailableVoices` currently concatenates supplied voices and STOCK_VOICES). Include a Reset filters action in the no-results state.

Acceptance: a user can audition two voices without changing the selected voice, see which engine can use the voice, and apply it to a persona or agent in the same picker. Sample playback never unexpectedly starts a call.

### P1 — Provider failures need recovery within the chosen task

Evidence: user's screenshot shows missing ElevenLabs Voices/Agents permissions while changing engines; `PersonaControls` leads to “Other call providers” and `NativeVoiceCall` setup. These are different call paths with different recognition behavior. The accuracy option only applies to the main Voice Call path.

Recommendation: label the distinction in one compact line: “Studio call — speech recheck available” versus “Direct provider call — provider recognition”. Engine selection should save independently from call connection. Show provider availability beside the engine and a repair/retry action on connect failure, retaining voice/language/accent. Do not expose server permission jargon as the sole user instruction; offer a working alternative when available.

Acceptance: selecting an engine never reconnects a call unexpectedly; failures preserve settings and show a next step; the user can tell whether the accuracy toggle applies to the current call.

### P2 — Simplify discovery and maintain persona context

Evidence: desktop primary navigation has six destinations while Persona Chat is in Explore more (`LeftSidebar.tsx:38–53`); mobile has Personas/Create/Tools/Library/More (`MobileNavigation.tsx:12–17`) with Super Agent and Chat behind More. Persona creation appears in global header, page and sidebar onboarding. The sidebar “New to the studio?” prompt is unconditional (`LeftSidebar.tsx:220`).

Recommendation: put Conversations (Persona Chat and Agent) in a predictable navigation group. On mobile either replace Tools with Conversations or make a stable Conversations shortcut on the Personas page, based on actual task frequency. Show onboarding CTA only when there are no personas or onboarding remains incomplete. Put active persona in one shared compact context control; clarify “No persona — create freely”. Retain context and drafts when moving between Create, Library and Edit.

Acceptance: Chat is discoverable in one navigation interaction on desktop/mobile, current destination is highlighted, returning to an editor restores draft and selected persona, and experienced accounts do not receive first-persona prompts.

### P2 — Agent Controls needs an intentional information architecture

Evidence: `AgentView.tsx:3166` opens an absolute 470px wrapping controls popover; nested Voice & agent setup is open by default; this includes brief, planning model, voice model, providers, clone voice and pilot call surfaces (`:3204–3349`). Composer is large and Plan/Build are explicit (`:3754–3866`), a good improvement. Message history has 44vh cap (`:3572`).

Recommendation: keep Plan/Build and the main prompt visible. Convert Controls to three compact sections: Task behavior, Voice, Project memory. Show only the selected provider's compatible models and voice choices; keep experimental pilots under Advanced. Put brief editing in Project memory, not Voice setup. Show estimated cost and execution approval only in Build plans; Plan should not expose execution CTAs. Replace raw model/effort telemetry above message content with expandable run details.

Acceptance: prompt plus Plan/Build, attach/research and Send are visible at laptop height; a user can switch voice in at most two interactions; controls do not extend off-screen or cover the composer irrecoverably; selected mode has observable matching behavior.

### P2 — Theme consistency and legibility

Evidence: `CreatePersonaPage.tsx:1427` hardcodes navy `#050914`; `CreatorHubView.tsx:45–101` has blue/sky/indigo tool colors; `AIToolsView.tsx:3045,3095` uses blue-to-indigo output CTAs; `GalleryView.tsx:767` uses blue; Planner at `:724,1169` uses cyan/violet; Voice at `:1163,1463` uses indigo/cyan; Revenue at `:208–245` uses cyan/violet/fuchsia. These bypass the existing theme tokens. Numerous helper/labels are 8–10px uppercase; motion uses transition-all and persistent decorative pulses.

Recommendation: bind surfaces, primary actions, focus rings and selected states to semantic studio tokens. Gold denotes the primary action/selection, restrained green/red/amber denote actual statuses. Replace provider decoration with text/icon labels. Keep helper labels at 12px and input/body at 14–16px; use weight and spacing rather than all-caps to create hierarchy. Audit contrast/keyboard focus and reduced motion separately before claiming accessibility conformance.

Acceptance: default theme has no decorative blue hues across all workspace pages; semantic statuses remain distinguishable; controls retain a visible keyboard focus state and usable target area without shrinking text to fit.

### P2 — Planning has redundant and inactive affordances

Evidence: Planner header RotateCcw button at `PlannerView.tsx:505` has no onClick or accessible label. Generate Weekly Plan and Regenerate Ideas both call handleGenerate, simultaneously visible at `:1163–1186`. Generate All Content sits beside them with a distinct gradient.

Recommendation: remove the inert header button. Show Generate plan in the empty state; once a plan exists, show Regenerate under an overflow menu with a preserve/replace choice. Separate planning from paid batch production: a “Create media from selected posts” flow with selection count, cost and progress. Keep scheduling clear about whether it is calendar organization or connected-platform publishing.

Acceptance: every visible button performs an action, only one main planning action appears, regenerating cannot silently replace edits, and batch generation clearly identifies which posts will be rendered.

### P2 — Library batch actions should match selection scope

Evidence: `GalleryView.tsx:328–382` calls the mode Select to upscale; its Download All action downloads filtered images rather than selected IDs. Toolbar mixes search/sort/upscale/download/layout; preview uses separate metadata scroll (`:692`).

Recommendation: rename mode Select and show a persistent contextual toolbar “N selected”: Download, Upscale compatible images, Move/Assign, Delete. Filtered collection downloads belong in an explicit “Download filtered images” menu action. Ensure search includes title/persona/type, not only prompts. Make filename/type/persona/date visible before opening an item. Keep preview Download primary and editing secondary.

Acceptance: selected actions operate on selected assets; filtered/export scope is stated; video/audio are not silently counted as downloadable images; failed downloads expose retry and batch completion summary.

## Suggested implementation sequence

1. Fix shell/call viewport contract and unmet-requirement messages; verify against the user's laptop viewport first.
2. Consolidate voice audition/selection/engine setup and provider failure recovery.
3. Apply shared charcoal/ivory/gold tokens and readable control styles across every rendered page, then perform a separate keyboard/contrast audit.
4. Simplify navigation, Agent controls, library selection and Planner CTAs.
5. Consolidate studio step/output patterns and improve draft persistence/error recovery.

## Verification plan and limits

Use an authenticated synthetic account with seeded empty, populated, long-history, queued, failed and unsupported-provider states. Compare 1440×900, 1280×800, 390×844 and 200% zoom/reflow. Walk create persona → audition → chat/call → request image → Library → edit → export and plan → build → review → execute → recover. Check keyboard-only focus, screen-reader names, Arabic/English text expansion and reduced motion. Paid tests should target provider boundaries only after free UI/state checks pass; capture returned output/job IDs and final assets without silently spending on broad repetitive generations. This report does not establish successful calls, pronunciation fidelity, paid provider capability, accessibility conformance or user-study results.
